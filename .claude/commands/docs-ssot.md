指示書の棚卸しを行う。対象: 「$ARGUMENTS」（空欄なら全体）。

**機械判定できる部分は `make docs/check` が既に見ている。本コマンドは判断が要る部分だけを扱う。**
検査の内容・除外理由・`ssot-assert` の記法は `scripts/docs-ssot-check.sh` 冒頭のコメントが正本。

## 1. 機械判定を先に通す

```
make docs/check
make docs/ssot
```

ERROR が残っている状態で判断作業に入らない。先に潰す。

## 2. WARN の始末を決める

WARN は「将来腐る形をしている」記述。放置してよいものは一つも無い。次のどれかに振り分ける。

| 判断 | 対応 |
| --- | --- |
| 実態から機械照合できる | 記述側に `ssot-assert` ディレクティブを添える |
| 原理的に照合できない | `ssot-assert: manual '<理由>'` で理由を残す。理由は「なぜ照合できないか」であって「今は正しいから」ではない |
| そもそも書く必要が無い | 記述を消す。時点依存の情報は指示書の中で最も腐りやすい |

検査自体が誤検出しているなら、個別に抑止せず**検査の定義を見直す**（`deterministic-verification.md` §2）。

## 3. 拘束力と影響度の突き合わせ

規約には強度の階層がある。**強い順に: 機械判定（CI が落ちる） > hook（ターンをブロック） > 常時ロードの本文 > 参照先の本文。**

AGENTS.md §1〜§3 の各規約について、次の2つを見て**逆転しているものを探す**。

- 現在の拘束力はどれか
- 違反したときの影響度（検出しやすさ・被害の大きさ）

影響が大きく検出しにくいのに参照先の本文でしか守られていないものが、次に機械検証へ移す候補。
移送先の選び方は `deterministic-verification.md` §1・§3（AST ベースを優先）。
移したら ROADMAP「横断施策：決定論的検証基盤」に記録する。

## 4. 経路の計測

代表的な問い（「層別カバレッジ閾値は」「テーブル駆動の正しい形は」「新機能をどう追加するか」など）
について、**ホップ数**（正本にたどり着くまでに開くファイル数）と**読み込み行数**を実測する。

- 常時ロードは `CLAUDE.md` + `AGENTS.md` の行数。毎ターン消費するので、ここに置くのは
  「毎ターン必要」か「違反頻度が高い」ものだけに絞れているかを見る
- 同じ問いに複数の経路があるなら、どれも正しい終点に着くかを確認する。片方が古びていたら SSoT 違反
- 4ホップを超える経路は、AGENTS.md §3 の索引表に行を足して直行できないか検討する

## 5. 読み手の確認

`.claude/**` は Claude Code 専用で、他の AI エージェントからは読めない。
規約の正本がそこに入っていないかを見る（`make docs/check` の検査5 が機械判定するが、
「正本」という語を使わずに実質的な正本になっている場合は人が見るしかない）。

配置ルールは AGENTS.md「指示書の読み手と置き場」が正本。

## 6. 報告

次の形で出す。所見だけで終わらせず、優先度と行数の増減まで出す。

1. 機械判定の結果（ERROR / WARN の件数と内訳）
2. 判断が要ったもの（WARN の振り分け結果と理由）
3. 拘束力が影響度に見合っていない規約の一覧
4. 経路指標の実測（問い → ホップ数 → 行数）
5. 整理案（優先度順・行数の増減つき）

指示書を変更したら、完了前に `make docs/check` を再実行する（AGENTS.md §6）。
commit / push はユーザーの明示指示があるまで行わない。
