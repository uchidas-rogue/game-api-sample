# レイヤードアーキテクチャ（Clean Architecture系）のテスト観点

Domain/Entity層・UseCase層・Repository層・DIコンテナ境界のような**明確な層構造とその境界を持つ設計**に固有のテスト観点を扱う。
層構造を前提としない一般的なテスト原則は [testing-principles.md](testing-principles.md)、静的検証は [deterministic-verification.md](deterministic-verification.md)、進め方は [tdd-workflow.md](tdd-workflow.md) を参照。ここでは重複させない。

## 0. 適用範囲

本ファイルが対象とするのは、以下のような性質を持つ設計である。

- 内側の層（ドメインモデル）が外側の層（永続化・外部I/O）に依存しない一方向の依存関係を持つ
- 永続化層がRepository等の抽象を介して差し替え可能になっている
- 複数の処理をひとまとまりの成功/失敗単位（トランザクション等）でくくる境界がある
- 依存性の解決（生成）をコンポジションルートに集約している

このような構造を持たない小規模なコード（層分けのないスクリプト等）には無理に適用しない。

4ファイル全体の役割分担の正本は [testing-principles.md](testing-principles.md) 0節であり、ここでは再掲しない。

## 1. 層構造がテスタビリティを決める

内側の層（ドメインモデル）が外部依存（永続化・グローバルな実行時状態等）を持たないという設計上の制約は、副次的な効果としてテストの単純化をもたらす。

- 内側の層に外部依存の使用を禁止すると、その層のテストは外部リソースの初期化・モック化が一切不要になり、[testing-principles.md](testing-principles.md) 3節の「値オブジェクトは実物を使う」がそのまま成立する
- 依存の向きとテストを書く順序は対応する。依存されない層（最も内側）から着手すると、後続の層のテストで前の層を安心してそのまま使える（[tdd-workflow.md](tdd-workflow.md) 2節「層の実装順序」の設計側の根拠）
- 依存禁止ルールに例外を作る場合（例: 定数参照のみ許可等）は、「参照」と「実行時の副作用を伴う依存」を区別し、後者のみを禁止対象にする

## 2. 内側の層には解決済みの値だけを渡す

外部由来の生データ（DBの生カラム値、設定の生構造等）の解釈・正規化は、内側の層の手前（外側の層）で完了させ、内側の層には「解決済みの単純な値（真偽値・列挙値等）」のみを渡す。

- この分離により、内側の層のテストは「真偽値・列挙値の組み合わせ」だけで完結し、外部データの生成・モック化が不要になる
- データソースが未確定の除外条件・分岐は、「常に固定値を返すフック」として内側の層に持たせておき、生データの解決は後続作業に回してもよい。これにより内側の層の設計・テストを先に完成させられる
- この原則が破られると（内側の層が生データの形式を知ってしまうと）、内側の層のテストに外部データ形式のモックが必要になり、[1節](#1-層構造がテスタビリティを決める)の利点が失われる

## 3. ドメインの不変条件はmutationメソッドで守る

エンティティ（ドメインモデル）の属性は読み取り専用として公開し、値の変更は必ず「不変条件（範囲・符号・状態遷移の可否等）を自ら保証する名前付きの業務メソッド」を経由させる。生の setter は公開しない。

- **最終防御はmutationメソッドに置く**。外部入力（呼び出し元の層からの引数）を直接受け取るのはこれらの業務メソッドであり、不正値の拒否責任もここに集約する。呼び出し側の層（ユースケース層等）で事前チェックしてからmutationメソッドを呼ぶ、という二重防御は行わない（[testing-principles.md](testing-principles.md) 5節「責務の重複禁止」と同じ考え方をドメイン層内部にも適用する）
- **生成用ファクトリ・復元用コンストラクタは対象外にできる**。信頼された内部境界（永続化層からの復元等、外部入力を直接受けない経路）だけから呼ばれるものは、値域検証・その境界値テストの対象外にしてよい。データの型・制約は元のデータソース（スキーマ等）側に委ね、二重実装しない
- **テストの焦点はmutationメソッドの境界**。不変条件のテスト（[testing-principles.md](testing-principles.md) 7節の境界値3基準）は、この「業務メソッドの引数」に対して行う。生成時の値そのままの組み合わせを網羅する必要はない
- この設計により、ドメイン層のテストは外部依存なしに「業務メソッドを呼んで不変条件が守られるか」だけを検証すればよくなり、[1節](#1-層構造がテスタビリティを決める)の単純化がエンティティの内部にも及ぶ

## 4. 集約ロジックはコレクションクラスに閉じ込める

複数件のデータに対する集計・フィルタ・探索といったビジネスロジックは、呼び出し元の層（オーケストレーション層等）に直接書かず、複数件をラップする専用のコレクションクラス（ファーストクラスコレクション）にカプセル化する。

- 永続化層から複数件を返す操作は、素の配列ではなく、上記コレクションクラスのインスタンスを返す
- 「所持数順に上限まで選ぶ」のような複数候補を横断する選択アルゴリズムも、呼び出し元でループを書かず、コレクションクラス自身のメソッドとして実装する。呼び出し元はコレクションのメソッドを呼ぶだけの薄いラッパーに徹する
- **この設計はテスト責務を明確に分割する**: 呼び出し元の層は集約ロジックの分岐網羅を担当しない（コレクションクラスに委譲しているため）。集約ロジックの境界値・分岐網羅（複数候補にまたがるケース、端数処理等）はコレクションクラス自身のテストでのみ担保する
- 呼び出し元の層のテストで、配列を直接ループして期待値を組み立てるようなテストコードが必要になった場合は、集約ロジックが誤って呼び出し元に漏れ出しているサインである

## 5. 永続化層（Repository等）のテスト必須ケース

Repositoryのような「オブジェクトと永続化ストレージの境界」を担う層は、CRUD一般に共通する以下のパターンについて必須テストケースを定める。

| パターン | 必須テストケース |
|---------|----------------|
| 単件取得（ロック無し） | レコードあり→ドメインオブジェクトに変換 / レコードなし→未取得を表す値を返す |
| 単件取得（ロック有り・更新目的） | レコードあり→ドメインオブジェクト + 内部の追跡状態に登録 / レコードなし→未取得 / 取得済みキーの再取得→同一インスタンスを返し再クエリしない / 1回目の変更が2回目の取得に反映される（**lost update防止**） |
| 新規作成 | 作成後の戻り値と渡したドメインオブジェクトを追跡状態に登録する / 作成直後の同一キーへの更新操作が二重作成ではなく更新経路になる / 作成失敗時（永続化層からの異常な戻り値）は例外にする |
| 読み取り（作成・ロック取得済みの反映） | 取得済み・作成済みのキーは再クエリせず同一インスタンスを返す |
| 複数件取得（一覧） | ロック済み行の差し替え / 未変更行はキャッシュ値のまま / 作成済み（まだ一覧に現れない）行は追加 / 権限外の行は除外 / 差し替えと追加が混在しても重複しない / 空一覧でも作成済み行は返る |
| 更新 | ロック取得済み→更新を発行する / ロック取得済みで同一キーへの複数回更新が成立する / **変更なし判定時は更新クエリを発行しない** / ロック未取得→更新を発行せず、作成でもない後続処理に委ねる |

- **「同一キーに対して同一トランザクション内で常に同一インスタンスを返す」（Identity Map相当の仕組み）は、read-modify-writeの連鎖（読む→変更する→別の操作でまた読む→書く）で後勝ち上書き（lost update）を防ぐための不変条件である**。この仕組みを検証するテストを削除・簡略化しない
- 複数件取得の必須ケースは「件数が合っているか」ではなく、上表の個々のシナリオ（差し替え・追加・除外・重複なし・空一覧）を独立したケースとして持つ（[testing-principles.md](testing-principles.md) 10節の「件数だけで合格にしない」の永続化層版）

## 6. 基底クラスとサブクラスのテスト責務分割

永続化層に「共通ヘルパーを提供する基底クラス」と「対象ごとの実装を持つサブクラス」という構造がある場合、テストの責務を以下のように分割する。

| 責務 | テスト対象 |
|------|-----------|
| [5節](#5-永続化層repository等のテスト必須ケース)の表にある分岐網羅（Identity Map・overlay等の汎用ロジック） | 基底クラスのテストで一度だけ担保する。サブクラスのテストで再現しない |
| 対象固有のレコード⇔ドメインオブジェクト変換ロジック | サブクラスのテストで検証する |
| **クエリ構築時の引数**（読み取り専用か更新目的でロックを取るか、対象データの所属範囲を絞る条件が正しいか等） | **サブクラスのテストでのみ検証可能**。基底クラスは「どんな引数でクエリが呼ばれたか」を知らないため、この検証は基底テストでは代替できない |

基底クラスのテストが手厚いことを理由に、サブクラス側の「クエリ構築引数の検証」を省略しない。ここを省略すると、意図した整合性レベル（読み取り専用のつもりが実は更新ロックを取っていた等）の欠落を検出できなくなる。

## 7. トランザクション境界の契約テスト

複数の操作をまとめて成功/失敗させる境界（トランザクション）を提供する仕組みは、以下の契約をテストで担保する。

| # | シナリオ | 期待される契約 |
|---|---------|----------------|
| 1 | 境界内の処理が失敗する | 失敗を検知し、取り消し処理（ロールバック相当）を実行してから、**元の失敗原因をそのまま再送出する**（取り消し処理の実行が失敗原因を別のものにすり替えない） |
| 2 | 取り消し処理自体が失敗する | 取り消し処理の失敗を握り潰さず、**それでも元の失敗原因を再送出する**（取り消し失敗のログは別途残してよいが、呼び出し元には元の原因を伝える） |
| 3 | 確定処理（コミット相当）自体が失敗する | 確定処理の失敗をそのまま呼び出し元に伝搬する |
| 4 | 境界内の処理が空の結果（値なし）で成功する | 空の結果を確定処理の対象として正しく確定し、値なしをそのまま返す（異常系と誤認しない） |

- この4シナリオは、境界を提供する仕組み自体（例: `Transaction` に相当するクラス）の単体テストで担保する。境界を使う側（ユースケース層）のテストでは境界自体をモックしてよく、境界の契約は境界自身のテストでのみ検証する
- 境界内で行う処理は「取り消し不可能な処理（ロック取得が必要な処理等）」に限定し、ロックを伴わない事前検証・値解決は境界の外で完了させる。境界の外で完了できる処理を境界内に持ち込むと、ロック保持時間が延び、並行処理時の待ち合わせが増える（テストとしては「境界に入る前に検証済みであること」を確認する）
- 複数の永続化対象に同時にロックを取る場合は、取得順序を決定的（例: 識別子の昇順）にする。この決定性はデッドロック回避のための不変条件であり、テストで取得順序を検証する場合は「常に同じ順序で要求されること」を確認する

## 8. DIとテストシームの規律

依存性注入（DI）を手動配線（コンストラクタ引数渡し等、フレームワークを使わない場合を含む）で行う設計では、以下をテストと運用の両面で守る。

- **生成箇所を1箇所（コンポジションルート）に集約する**。層をまたいだ複数箇所でオブジェクトを生成すると、[5節](#5-永続化層repository等のテスト必須ケース)のIdentity Map等、リクエスト単位で一意であるべき状態が複数系統に分裂し、不変条件が壊れる。テストでも「コンポジションルート以外の場所から生成されていないこと」を確認できると良い（静的検証で担保する場合は [deterministic-verification.md](deterministic-verification.md) 9節参照）
- **テスト用の差し替え口（シーム）を本番コードから使わせない**。テストの都合で用意した差し替え可能な注入ポイントに、本番コードから参照可能なアクセサ（getter）を公開すると、本番コードが誤ってテスト用の差し替え経路を辿れてしまう。差し替え口は内部実装として隠し、外部からは通常の呼び出し経路のみを公開する

## 9. エラーの層別責務とテスト位置

層をまたいで例外・エラーを伝搬させる設計では、「どの層がエラーの意味づけ（種別の決定）をするか」を一意に決め、テストもその層でのみ意味づけを検証する。

- 各層が独自の判断でエラー種別・メッセージを決めると、同じ失敗原因が呼び出し経路によって異なるエラー種別として観測され、テストの期待値が場当たり的になる
- **最下層（既存の実装をラップするだけの薄い層等）は、失敗の意味づけをせず、成否を単純な形（真偽値等）で返すだけに留める**。同じ最下層の実装が複数の上位処理から再利用される場合、最下層がエラー名を決めてしまうと、名前と実際の呼び出し文脈が乖離するため
- エラーの意味づけは、その失敗が何を意味するかを判断できる立場の層（多くの場合、業務判断を行うユースケース層）に集約する。テストは「意味づけをする層で、意味づけが正しく行われているか」を検証し、最下層のテストでは「成否がそのまま伝わるか」だけを検証する
- 上位層がエラーを判定する際は、単一の判別可能なキー・属性のみで判定する契約にする。判定条件を複数箇所に分散させない

## 10. 共有状態・不変性のテスト観点

プロセスやインスタンスがリクエスト・呼び出しをまたいで再利用される実行環境（長時間稼働するワーカープロセス等）では、状態の意図しない共有がテストで検出すべき重大な不具合になる。

- インスタンスが複数の呼び出し単位（リクエスト等）をまたいで生存する設計（シングルトンキャッシュ等）を避け、呼び出しごとに新しいインスタンスを生成する設計にする。テストでは「別呼び出しのインスタンスが前回の状態を引き継がないこと」を確認する
- 設定値・定数を保持するオブジェクトを不変（イミュータブル）にする場合、生成後の値変更を許さない設計にする。テストで一時的に異なる値を使いたい場合は、共有インスタンスの値を書き換えるのではなく、**別の値を持つ新しいインスタンスを生成する**。共有インスタンスを書き換えるテストは、他のテスト（並行実行される場合は他の呼び出しも含む）に汚染を波及させる

## 11. 層別カバレッジ目標とレガシー境界の扱い

層構造を持つ設計にカバレッジ目標（[testing-principles.md](testing-principles.md) 11節）を適用する際、新規に設計する層と既存資産をラップする層とで目標達成の難易度が異なる。

- 新規に設計するコア層（ドメイン・ユースケース・新設のRepository等）は、外部依存を持たない設計にできるため、高いカバレッジ目標を適用しやすい
- 既存の大規模・複雑な資産（レガシーコード）をそのまま利用する箇所は、目標達成が著しく困難な場合がある。その場合、既存資産自体に高いカバレッジを求めるのではなく、**新設する境界層（ラッパー）側で入出力の契約を保証するテストを整備し、そちらでカバレッジ目標を達成する**（アンチコラプション層的な発想）。既存資産の内部までは踏み込まない
- この判断（目標達成困難と判断してラッパー側に責務を移す）を行った場合は、その理由をコードコメントやドキュメントに残し、目標を下げたのではなく責務の置き場所を変えたことを明確にする
