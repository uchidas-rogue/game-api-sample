# テスト設計文書の運用ルール

**本ファイルが「設計図とテスト仕様表をどう作り、どう保守するか」の正本。**
他の指示書（AGENTS.md §3・`.claude/**`）は本ファイルへリンクするだけで、以下の内容を再掲しない。

一般原則（言語・プロジェクト非依存の考え方）は [principles/tdd-workflow.md](principles/tdd-workflow.md) §3〜§9 にある。
本ファイルはそれを本リポジトリに適用した運用形であり、両者が食い違ったら本ファイルを優先する。

## 0. このディレクトリの構成

| 置き場 | 内容 | 読み手 |
| --- | --- | --- |
| `principles/*.md` | 言語・プロジェクト非依存のテスト設計原則（4ファイル） | 全 AI エージェント・人間 |
| 本ファイル | 設計図とテスト仕様表の運用ルール | 同上 |
| `<機能>.md` | 機能ごとのフロー図とテスト仕様表 | 同上 |

## 1. 何を作るか（対象の性質で決める）

| 対象の性質 | 本リポジトリでの該当 | 作るもの |
| --- | --- | --- |
| 手順・分岐を持つ処理 | `internal/usecase/**`, `internal/driver/**` | **フローチャート**（mermaid）+ テスト仕様表 |
| 意味のある状態を持ち、遷移の可否が重要なエンティティ | 現時点で該当なし（将来 outbox のステータス遷移が候補） | 状態遷移図 + テスト仕様表 |
| 単純な計算・バリデーション・値オブジェクト | `internal/domain/**` | **図を作らない。テストコードのケース配列自体を正本**とし、各ケースに意図の注記を添える |

**契約表・決定表は作らない。** テストと同じ情報を別ファイルに書くと、片方だけ更新されてドリフトする。
図を作らない対象については、テストコードが唯一の正本になる。

## 2. 作る順序

1. **設計図 + テスト仕様表**
2. **テストコード**（この時点では失敗する = RED）
3. **実装**（テストを通す = GREEN）

コードだけを先行させない。図とテストが先にあることで、実装者の思い込みではなく
「レビュー可能な形の合意」を先に固定できる。

層の実装順序は依存の少ない側から: `domain` → `usecase`（モック使用）→ `infrastructure`。

## 3. テスト仕様表の形

| 列 | 内容 |
| --- | --- |
| ケース番号 | 1 始まりの連番。欠番を作らない（削除したら詰める） |
| 条件 | テストケース名に対応する短い説明 |
| 図のパス | フロー図のノード ID を経路として連結（例: `A→B→C→E4`） |
| 期待結果 | 戻り値・エラー・状態変化 |
| 検証すべき呼び出し | 下位層の呼び出し（引数・回数）。`driver` 層など失敗経路が複数ある対象で追加する |

**表の1行 = テストコードの1ケース。** この1対1対応が崩れたら、どちらかが古い。

### 並び順と重複排除

- **図のパスが短い順**に並べる。エラー・早期リターンが先、正常系のフルフローが後
- 同じ長さのパスが複数あるときは エラー → 境界値 → 正常系 の順
- **同一パスを通るケースは1つに統合する**。同じコードパスなので、ケースを増やしても検出力は上がらない
  - 「戻り値のエラーが sentinel か一般エラーか」の違いだけなら同一パス。統合する
  - 分岐の通過が1つでも違えば別ケース

## 4. カバレッジとの関係

Go の `go test -cover` は**文カバレッジしか出さない**（分岐カバレッジを出す標準手段が無い）。
そのため **分岐の網羅はこの設計図のパスカバレッジで担保する**。

- 文カバレッジ = `make test/cover/check` による CI の機械判定
- 分岐カバレッジ（代替: パスカバレッジ）= 本ファイルのチェックリストによる**レビューゲート**

フロー図を作る対象（`usecase` / `driver`）でこの文書を省略すると、**分岐の担保手段が完全に失われる**。

## 5. 図の保守ルール

実装を変更したとき、以下のいずれかに該当したら**対応する図の更新は必須**。

1. 処理ノードの追加・削除
2. 分岐条件の変更
3. 下位層への呼び出し内容の変更
4. 戻り値・出力構造の変更

**更新順序は 図 → テスト → 実装** を維持する。コードだけ先に変えない。

## 6. レビューゲート用チェックリスト

設計図・テスト仕様表・テストコードのいずれかを変更する PR で確認する。
**この6項目が正本。** 他の指示書で項目を抜粋・再掲しない（間引かれた写しができるため）。

- [ ] テスト仕様表のケース番号とテストコードのケース順が一致している
- [ ] テスト仕様表の「図のパス」の数（重複排除後）とテストコードのケース数が一致している
- [ ] 図中のすべての終端ノード（正常終了・各エラー）に、対応するケースが最低1件ある
- [ ] 各パスで検証すべき下位層の呼び出し（引数・回数）を確認している
- [ ] 同一パスの重複ケースが排除されている
- [ ] ケースが「パスが短い順」に並んでいる

## 7. ファイルの置き方

- 機能単位で1ファイル（例: `gacha.md`）
- 1ファイル内に、対象メソッドごとの「フロー図 + テスト仕様表」を並べる
- 未解決の穴（図にはあるがテストが無いパス）は **`未対応` として表に残す**。消さない
