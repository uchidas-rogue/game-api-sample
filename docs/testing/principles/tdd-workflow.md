# TDDワークフローの原則

「何を（どんな順序で）作るか」に関する進め方の原則。
テストコード自体の品質は [testing-principles.md](testing-principles.md)、静的検証の設計は [deterministic-verification.md](deterministic-verification.md)、層構造・境界を持つ設計固有の観点は [layered-architecture-testing.md](layered-architecture-testing.md) を参照。ここでは重複させない。

## 1. 成果物の作成順序（図 → テスト → 実装）

新しい処理（ユースケース・ハンドラ等）を追加する際は、以下の順序で成果物を作成する。

1. **設計図**（フローチャート・状態遷移図等。3節参照）+ テスト仕様表
2. **テストコード**（RED状態。実装がまだ無いので失敗する）
3. **実装コード**（テストを通す。GREEN化）

**コードだけを先行させてはならない**。図とテストが先に存在することで、実装者の思い込みではなく設計上の合意（レビュー可能な形）を先に固定できる。

## 2. 層の実装順序

レイヤードアーキテクチャの場合、依存の少ない層から実装・テストする。

1. **値オブジェクト/ドメイン層を先にテストする**（外部依存なし。最も高速にRED/GREENを回せる）
2. **ユースケース/オーケストレーション層をモックテストする**（下位の協調オブジェクトをテスト用モックに差し替える）
3. **インフラ層（永続化等）は単体テストと統合テストの両方で担保する**: 実リソースなしに検証できる振る舞い（Identity Map等の既定パターン。詳細: [layered-architecture-testing.md](layered-architecture-testing.md) 5節）は単体テストで先に担保し、実リソースとの結合部分（接続設定・クエリ構文・スキーマ整合等）のみを統合テストで補完する。実行速度・環境依存を理由に最後に回すのはあくまで「実リソースとの結合確認」であり、振る舞いの検証を先送りにしてはならない

この順序にすることで、下位層のバグを先に潰してから上位層のテストに進める（上位層のテスト失敗が下位層由来なのか上位層由来なのか切り分けやすい）。

## 3. フロー図を設計源にする

対象の性質によって、作るべき設計図の種類を使い分ける。

| 対象の性質 | 設計図 | テスト仕様表の持ち方 |
|-----------|--------|---------------------|
| 手順・分岐を持つ処理（ユースケース、ハンドラ） | フローチャート（処理の流れ図） | 図とは別にテスト仕様表を作り、テストケース配列にマッピングする |
| 複数の意味のある状態を持ち、遷移の可否が重要なエンティティ | 状態遷移図 | 同上。ただし契約表・決定表という別文書は作らない（テストとの重複でドリフトするため） |
| 単純な計算・バリデーション・状態を持たない値オブジェクト | 図は作らない | **テストコードのテストケース配列自体をSSoT（唯一の真実の源）とする**。各ケースに意図を説明する短い注記（given/when/then相当）を添える |

**契約表・決定表のような「テストと同じ情報を別ファイルに書く」文書は作らない**。同じ情報を2箇所に持つとドリフト（片方だけ更新される）が発生するため、テストコード自体を正本にする。

## 4. テスト仕様表の構造

フロー図を作る対象については、以下の列を持つテスト仕様表を作成する。

| 列 | 説明 |
|----|------|
| 対象メソッド/関数名 | テスト対象 |
| ケース番号 | 1始まり連番。欠番不可（削除したら詰める） |
| 条件（シナリオ概要） | テストケース名に対応 |
| **図のパス** | フロー図のノードIDを経路として連結したもの（例: `A→B→C→ERR1`）。分岐条件がある場合は分岐先の条件も注記する |
| 期待結果 | 戻り値・状態変化・呼び出し回数など |

**テスト仕様表の1行 = テストコードの1テストケース**という1対1対応を維持する。この対応により「図で表現された仕様」と「実行されるテスト」の乖離を防げる。

外部インターフェース層（ハンドラ等）で複数の失敗経路がある場合は、この基本列に加えて「検証すべき呼び出し」（下位層の呼び出し引数、エラー通知の呼び出しコード等）の列を追加する。

## 5. ケースの重複排除

**フロー図上で同一の経路（同一パス）を通るケースは、1つのテストケースに統合する**。

- 同一パス＝同一コードパスであるため、パスが同じ複数のケース（例: 「ケースA」「ケースAの言い換え」）を別々にテストしても実行される命令列は変わらず、テストの本数が増えるだけで検出力は上がらない
- パスが異なる（少なくとも1つの分岐の通過が異なる）場合のみ、別ケースとして扱う

## 6. ケース並び順

テスト仕様表・テストコードのケースは、**フロー図のパスが短い順（経由ノード数が少ない順）**に並べる。

- 短いパス（エラー・早期リターン）を先に、長いパス（正常系のフルフロー）を後に置く
- 同じ長さのパスが複数ある場合は、エラーケース → 境界値 → 正常系の順にする

この並びにより、「どの分岐でフローが枝分かれするか」を表の上から順に追いやすくなる。

## 7. パスカバレッジによる網羅

処理の複雑さが「入出力の値のパターン」ではなく「経由する分岐・エラー処理の段階」に起因する層（特に外部インターフェース層）では、**入出力の値のバリエーションではなくフローのパス（経路）を網羅する**ことをテストの目標にする。

- 失敗処理が複数の段階（例: 「業務エラーとして構造化された失敗」「想定内だが構造化されていない失敗」「想定外の失敗」）に分かれる設計の場合、提供形態・処理系統ごとに「最低限満たすべきパス数」を定義する
- 各パスで、そのパスを通った際に呼ばれるべき下位層の呼び出し（引数・回数）まで検証する。単に「例外が飛ぶこと」だけでなく「正しい経路で正しい変換処理が呼ばれたこと」を確認する

## 8. 図↔テストの対応チェックリスト

設計図とテストファイルを作成・変更する際は、以下をレビューゲートとして確認する。

- [ ] テスト仕様表のケース番号とテストコードのケース番号が一致している
- [ ] テスト仕様表の「図のパス」の数（重複排除後）と、テストコードのケース数が一致している
- [ ] 提供形態・処理系統ごとに必要な最低パス数を満たしている
- [ ] 各パスで検証すべき呼び出し（引数・回数）を確認している
- [ ] 同一パスの重複ケースが排除されている
- [ ] ケースが「パスが短い順」に並んでいる

このチェックリストを設計変更のたびに回すことで、「コードだけ直してテスト仕様表を更新し忘れる」ドリフトを防ぐ。

## 9. 図の保守ルール

実装コードを変更する際、以下のいずれかに該当する場合は対応する設計図の更新が**必須**とする。

1. 処理ノードの追加・削除
2. 分岐条件の変更
3. 下位層への呼び出し内容の変更
4. 戻り値・出力構造の変更

**更新順序は「図の更新 → テストの変更 → 実装の変更」を維持する**。コードだけを先に変更し、図やテストを後回しにしてはならない（1節の作成順序と同じ原則を、変更時にも適用する）。

## 10. カバレッジを受入基準にする

実装が完了したと判断する基準に、カバレッジ数値（行・分岐カバレッジ、[testing-principles.md](testing-principles.md) 11節参照）を用いる。これにより「完了」の判断を主観に頼らず客観化できる。

- **既存のテストにケースを追加すべきかどうかは、まず現状のカバレッジを実計測してから判断する**。計測せずに「たぶん足りているはず」で追加要否を決めない

## 11. 改善ループと打ち切り

カバレッジが目標未達の場合、以下のサイクルで改善する。**このループには必ず試行回数の上限を設ける**（無限に未達ケースを探し続けない）。

1. **未カバー行/分岐の特定**: カバレッジ計測ツールの詳細出力から、実行されていない行・分岐を抽出する
2. **到達可能性の判定**: 各未カバー箇所を以下に分類する

   | 分類 | 対応 |
   |------|------|
   | 通常の分岐（到達可能） | テストケースを追加する |
   | エントリポイント関数本体等、設計上テスト対象コードパスの外にあるもの | スキップ（[testing-principles.md](testing-principles.md) 11節の「関数カバレッジは参考値」に該当） |
   | デッドコード（到達不可能） | スキップし、リファクタ候補として報告する |
   | 外部要因に強く依存し再現が困難なもの | 再現可能ならテスト追加、困難ならスキップして報告する |

3. **到達可能と判定した箇所のみ**テストケースを追加する
4. 再計測する

**過剰モック禁止**: 「到達可能性の判定」を経ずに、未カバー行を無理やり実行させるためだけの不自然なモック・テストケースを追加しない。デッドコードや設計上の制約をテストで無理にカバーしようとすると、テストが実装の都合に引きずられて可読性・保守性が下がる。

**試行上限に達しても未達の場合**: 改善作業を打ち切り、未カバー箇所の内訳（行・分類・理由）を報告する。数値目標の達成を無限に追求せず、「なぜ未達か」を人間が判断できる形で終了する。

## 12. 縮約時の分岐カバレッジの罠

複数の呼び出し元が同じ共有処理（ヘルパー関数等）を呼んでいる場合、「共有処理を直接テストして1回網羅し、各呼び出し元のテストは代表1件に絞る」という縮約をしたくなる。だが縮約の仕方を誤ると分岐カバレッジが激減するため、以下を区別する。

| 分岐の種類 | 具体例 | 統合可否 |
|-----------|--------|---------|
| 共有処理の**内部**にある分岐 | 共有ヘルパー内の条件分岐 | 単一のソース箇所に存在するため、どの呼び出し元経由でも1回通ればそのカバレッジは満たされる。**安全に1回へ統合してよい** |
| 各呼び出し元に**個別に書かれた**条件文 | 各呼び出し元が持つ独自のガード条件（認可チェックの成否分岐等） | 共有処理を呼んでいても、呼び出し元の条件行自体は呼び出し元ごとに**別々のソース行**。カバレッジツールは行単位で計測するため、呼び出し元の数だけ真偽両方を踏まないと分岐カバレッジが落ちる |

- **判断基準**: 統合してよいか迷ったら「その分岐の条件文はソースコード上に何箇所存在するか」を確認する。1箇所（共有処理内）なら統合可、複数箇所（各呼び出し元にコピペ）なら各箇所ごとに最低1回は真偽両方のテストケースが必要
- **縮約してよい例**: 同じ分岐を何度も「異なる入力値」でテストしているだけのケース（分岐は同一なので代表1件でよい）
- **縮約してはいけない例**: 各呼び出し元固有の条件行（同じ関数名でも呼び出し元ごとに独立して存在する条件式）
- **作業フロー**: (1) リファクタ・縮約後は必ずカバレッジを再計測する (2) カバレッジが下がったら「どの行が未網羅か」を疑い、詳細レポートで原因を特定する (3) 計画外の劣化を発見したら、黙って戻さずに縮約方針自体の見直しが必要かを含めて報告し、方針を確認してから修正する

## 13. チャンク分割とレビュー挿入

複数ファイルにまたがる大きな変更は、一度に実行せず、レビュー可能な単位（チャンク）に分割し、**チャンクごとに完了させて都度レビューを受けてから次に進む**。

- 理由1: 変更ファイル数が多いと人間がレビューしきれなくなる
- 理由2: 実行系（自動生成・自動実装ツール等）も、一度に扱う範囲が大きくなるほど出力品質が劣化しやすい
- 大きな計画を一括で最後まで実行せず、区切りごとに立ち止まる運用にする
