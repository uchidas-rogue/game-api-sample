設計判断とその理由

「何を作ったか」より「なぜそうしたか」を残すことを重視しています。以下は主要な判断と、その根拠になった実測値です。

書き込みと参照を分ける（CQRS + outbox）

スコア加算は MySQL のトランザクションで確定させ、同じトランザクション内で outbox イベントを INSERT。 ギルドへの合算と Redis 反映は worker が非同期に行います。ランキング参照は Redis の Sorted Set だけを見るため、 参照負荷が書き込み DB を圧迫しません。

根拠: docs/plans/guild-score-async.md / docs/testing/outbox-worker.md

イベント単位 tx → バッチ tx（COMMIT 回数を 1/batchSize に）

負荷試験で「API のレイテンシは基準内なのに worker が生産レートに追いつかない」ことが判明。 1件ごとの COMMIT（fsync）が上限を決めていたため、バッチ単位の適用へ変更しました。 消化レートは 約 33/sec → 270〜315/sec（ピーク 543）、 ピーク pending は 111,613 件 → 35〜45 件。

ただしバッチは1件の恒久失敗で全体が止まるため、失敗時だけイベント単位経路へ退避する二段構えにしています。

根拠: 負荷試験 make load/points（約 407 req/sec × 100 秒）

worker のトランザクションを READ COMMITTED にする

worker の SELECT ... FOR UPDATE が REPEATABLE READ でギャップロックを取り、 API 側の outbox INSERT を INSERT_INTENTION 待ちでブロックしていました （API の p95 が 108ms → 4.6s）。worker は同一 tx 内の読み取り一貫性に依存しないため、 分離レベルを下げて解消しています。

根拠: docs/testing/transaction-boundary.md「分離レベルの使い分け」

ランキングの「空」と「未初期化」を区別する

Redis が揮発すると ZREVRANGE はエラーではなく空配列を返します。「誰も加点していない」と 「ランキングが消えている」を取り違えないよう、センチネルキーで初期化済みかを判定し、 未初期化なら 503 と Retry-After を返します。

根拠: docs/testing/ranking.md §0

同じユースケースを HTTP と gRPC の 2 経路で配る

Unity クライアント向けに gRPC を足しました。usecase 層を 1 行も変えずに済み、 cmd/api と cmd/grpc は同じインスタンスを共有しています。 この境界は申し合わせではなく depguard が保証していて、driver から infrastructure を import した時点で lint が落ちます。

リアルタイム配信は既存の outbox 基盤に接続しました。worker が Redis へ反映を終えた直後に publish し、server streaming がそれを購読して push します。既存の worker 起床通知は 反映前に飛ぶので転用できない、という判別がいちばん間違えやすい箇所でした。

根拠: docs/testing/grpc-ranking.md / ranking-watch.md

意図的にやらないことを書き残す

WAF は導入しません（エンドユーザーが k6 なので、レートベースルールが負荷試験結果を歪めるため）。 NAT Gateway も AZ 冗長化せずコストを優先しています。判断の理由とトレードオフを terraform/ARCHITECTURE.md の「対象外」節に明記しています。

根拠: terraform/ARCHITECTURE.md / ROADMAP.md フェーズ2

AI エージェントとの開発体制

実装は Claude Code 主体で進めています。人が毎回同じ指摘をしなくて済むよう、 規約を「AI が読む助言」から「CI で落ちる判定」へ移し続けることをプロジェクトの横断施策に据えました。

規約の正本を1箇所に置く

規約の正本は AGENTS.md と docs/。Claude 専用の CLAUDE.md / .claude/** には正本を置きません（他のエージェントから読めないため）。 この制約自体を make docs/check が判定し、正本の重複や実態との乖離を CI で落とします。

図 → 失敗するテスト → 実装

usecase / driver の変更は、実装より先に mermaid のフローチャートと テスト仕様表を書きます。Go には分岐カバレッジを出す標準手段が無いため、 図のパスカバレッジで分岐の網羅を代替する設計です。

判定へ移した規約（Phase 0〜8）

  • 層間 import → depguard
  • ログ・ミドルウェア順序・テストの共有状態 → ruleguard の自前 AST ルール
  • var _ Iface = (*T)(nil) の配置 → scripts/archcheck
  • 仕様表とテストの対応（件数・順序・図の終端網羅） → scripts/doccheck
  • 生成物の drift・層別カバレッジ・指示書の SSoT → 各 make ターゲット

検査を足すときの原則は「その検査が捕捉する既知の実例を必ず書く」。 実例を伴わない検査は誤検出源になり、いずれ無効化されるためです。

「AI が読める構造か」を外から確かめる

外部サービスの DeepWiki にリポジトリを読ませたところ、層ごとの解説と依存フロー図を持つ 8 セクションのドキュメントが自動生成されました。自分で書いた指示書を自分の AI に読ませて うまくいった、で終わらせないための外形的な確認として置いています。

役割は下のチャットと補完関係です。DeepWiki が答えるのは「コードがどうなっているか」、 チャットが答えるのは「なぜそうしたか」。正本は文書側に置いたままで、 DeepWiki は特定コミット時点の自動生成物なので参考扱いです。
